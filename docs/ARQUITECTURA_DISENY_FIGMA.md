# Editor visual del storefront + importación de Figma

Sustituye el alcance corto de `admin/disseny-web` (constructor de bloques fijos, ver `api/app/blocks/registry.py` + `web/components/store/blocks/registry.js`) por un editor visual real por tenant, con importación de diseños desde Figma. Decidido en conversación (2026-09-27): **construcción propia, dependencia de terceros mínima y solo en forma de librería vendorizable (MIT, sin servicio cloud ni licencia AGPL de por medio)**, nunca delegando el motor de edición ni el almacenamiento del contenido a una plataforma externa (Builder.io, Plasmic) — se evaluaron y se descartaron por esto: contenido fuera de nuestro Postgres, coste recurrente por tenant, o licencia AGPL sobre la pieza que se autohospedaría.

**Estado (2026-09-28): Fase 0 y Fase 1 cerradas del todo, probadas en vivo en dev** (modelo de datos, CRUD admin de `Page`, renderer SSR real, routing multi-página unificado con `Pagina`, nodos protegidos de checkout con validación de publicación — ver bitácora en §5). **Sin commitear todavía** (ver nota al final del documento). Fases 2-5 (editor visual, OAuth Figma, import estructural, migración/retirada de `HomeBlock`/`Pagina`) siguen sin empezar — son el siguiente paso.

---

## 1. Alcance decidido

- **Autoservicio por tenant**: cada tenant conecta su propia cuenta de Figma (OAuth) desde su panel de admin y lanza la importación cuando quiera — no es un proceso operado por nosotros.
- **Editor visual libre** (no solo presets curados): un tenant puede componer secciones con layout/estilo configurable, no limitado a las variantes de bloque que ya existen hoy.
- **Toda la web es editable, incluido checkout/carrito** (decisión 2026-09-27, revierte una recomendación anterior de dejarlos fuera): se consigue sin arriesgar la lógica de negocio mediante "nodos protegidos" — ver §3d.
- **Todo en casa**: modelo de datos, renderer SSR, pipeline de importación de Figma y mecánica del editor son código propio en este repo. Si en algún punto conviene apoyarse en una librería concreta para la mecánica de arrastrar/soltar (p. ej. Craft.js o `@dnd-kit`, MIT, sin servicio detrás), se vendoriza como cualquier otra dependencia de `package.json` — nunca como una plataforma externa de la que dependa el contenido o el hosting.

## 2. Lo que ya existe y se reutiliza

- **Theming por tenant**: `ConfiguracioBotiga.theme` (JSON, schema `ThemeTokens`) + `custom_css` saneado (`services/sanitize.py::sanitize_custom_css`) — ya inyectado en `web/app/layout.jsx`. El nuevo editor sigue usando estos tokens como fuente de colores/tipografía, no los duplica.
- **Constructor actual**: `HomeBlock` (modelo) + `api/app/blocks/registry.py` (schema Pydantic por tipo de bloque) + `web/components/store/blocks/registry.js` (componente React) + UI en `admin/disseny-web`. Se mantiene funcionando en paralelo mientras se construye el nuevo sistema — ningún tenant en producción (Ultra Local Records, la resta) puede quedarse sin home renderizable durante la migración.
- **Secretos por tenant**: `api/app/tenant_secrets.py` (`TenantSecrets`, AWS Secrets Manager + caché Redis, ya usado para Discogs/Spotify/Redsys). El token OAuth de Figma sigue este mismo patrón — nunca en `config.py` (que es global de plataforma).
- **Async**: `celery_app.py` / `tasks/` ya montado — necesario porque leer un fichero Figma completo y exportar imágenes no puede ser síncrono en el request.
- **Aislamiento multi-tenant y features**: `tenant_features` (`models/platform.py::TenantFeature`) — el editor nuevo se activa por tenant como un feature flag más, permitiendo rollout gradual sin tocar el resto.
- **Regla de oro que no cambia**: los nodos del editor nunca llevan datos de catálogo en vivo en sus props — igual que hoy con los bloques, el backend sigue resolviendo catálogo/carrito/checkout en cada request. El editor puede posicionar y estilar un `product_grid`, pero nunca puede alterar el comportamiento interno de un nodo que toque lógica sensible (stock, precios, pagos) — ver "nodos protegidos" en §3.

## 3. Modelo de datos (validado en conversación 2026-09-27, pendiente de escribir migración)

Naming en inglés (canon de DB/API fijado en `ARQUITECTURA_CORE_VERTICAL.md` §3), tres tablas nuevas, todas `TenantScoped`:

**a) `pages`** — sustituye `HomeBlock`, **multi-página desde el día uno** (no solo home: el tenant necesita poder crear cualquier página, no únicamente construir la portada).
```
id, tenant_id (TenantScoped), slug: str(100)
draft_tree: JSON
published_tree: JSON | None
seo_title / seo_description: JSON  {ca, es, en}
created_at, updated_at
UniqueConstraint(tenant_id, slug)
```
- **Draft/publish simple** (sin tabla de versiones/historial en v1): publicar = copiar `draft_tree` → `published_tree`. Se añade historial más adelante si hace falta, sin romper esto.
- El árbol es **un único JSON blob** por página (no filas por nodo con `parent_id`): mismo criterio que `theme`/`Release.tracklist`/`Order.shipping_address` — siempre se carga la página entera para editar o renderizar, nunca hace falta consultar nodos sueltos entre tenants. Cada nodo del árbol:
  ```json
  {
    "id": "n_ab12",
    "type": "stack | section | text | image | button | product_grid | ...",
    "props": { "title": {"ca": "...", "es": "...", "en": ""}, ... },
    "style": { "background": {...}, "spacing": {...}, "responsive": {"mobile": {...}} },
    "children": [ ... ]
  }
  ```
  Los campos de texto usan de entrada el patrón `{ca, es, en}` con fallback a catalán acordado en `docs/PLAN_MULTIIDIOMA_CONTINGUT.md` — el árbol nuevo nace ya multi-idioma, no arrastra el defecto de `HomeBlock.props` (ese plan sigue aparcado y solo aplicaría a `HomeBlock`, que se jubila en la Fase 5; no se invierte en arreglarlo dos veces). Cada tipo de nodo valida sus `props`/`style` con un schema Pydantic propio, mismo patrón que `blocks/registry.py` hoy, extendido para permitir anidar (`children`).

**b) `figma_connections`** — metadatos no sensibles, uno por tenant:
```
id, tenant_id (TenantScoped, unique)
figma_user_id / figma_handle: str   -- solo para mostrar "Conectado como..." en el admin
connected_at
```
El `access_token`/`refresh_token` no viven aquí: se añaden a `TenantSecrets` (`tenant_secrets.py`) como `figma_access_token`/`figma_refresh_token`, mismo patrón que `discogs_token` — nunca en una tabla propia ni en `config.py`.

**c) `figma_import_jobs`**
```
id, tenant_id (TenantScoped)
figma_file_key: str
status: pending | processing | ready | error
error_message: str | None
raw_snapshot_path: str | None   -- puntero a /uploads (mismo mecanismo que ReleaseImage), NUNCA el JSON crudo de Figma inline en Postgres — un fichero complejo puede pesar varios MB
result_tree: JSON | None        -- borrador propuesto, nunca se escribe directo a published_tree
target_page_id: FK -> pages.id | None
created_at, updated_at
```

### d) Nodos protegidos y páginas funcionales (checkout/carrito editables sin arriesgar negocio)

Checkout y carrito **podrán** pasar a ser `pages` normales (antes quedaban fuera del árbol) — pero su árbol incluye **nodos de tipo protegido**, mismo concepto que los nodos "vivos" ya existentes (`product_grid`/`carousel`), extendido con dos garantías nuevas. **Estado 2026-09-28**: el mecanismo (vocabulario de tipos protegidos, `requires_nodes`, validación de publicación) ya existe y está probado — lo que sigue sin hacer es la conversión real de `web/app/[locale]/checkout`/`carret` (páginas Next.js hardcoded hoy) a instancias de `Page` con estos nodos, y los componentes React `checkout_form`/`cart_summary`/`payment_widget` en `pageTree/nodes/`. Eso es trabajo de integración deliberadamente fuera de esta pieza — el riesgo más alto del documento (§6) — y se aborda junto con o después de la Fase 2 (editor), no antes.

- **No editables por dentro**: `checkout_form`, `cart_summary`, `payment_widget` (vocabulario ya fijado en `schemas/storefront.py::PROTECTED_NODE_TYPES`) no exponen props que alteren su comportamiento — solo posición dentro del árbol y estilo (color, spacing, ancho). La reserva de stock, el snapshot de precio/dirección y la llamada a la pasarela siguen resueltas 100% en backend, igual que hoy — nada de esto cambia hasta que se construyan esos nodos de verdad.
- **No borrables**: cada `page` puede marcarse `requires_nodes: ["checkout_form", "cart_summary"]` (lista de tipos obligatorios, **implementado y probado en vivo el 2026-09-28** — columna `Page.requires_nodes`, migración `a6a451afd252`). Al publicar (`draft_tree` → `published_tree`), el backend revalida que los tipos requeridos siguen presentes en el árbol — si falta alguno, la publicación se rechaza (422, `routers/pages.py::publish_page`), mismo criterio que otras invariantes del sistema (p. ej. `PesNoConfigurat` en `services/enviament.py`). Esto ya evita publicar un checkout roto por accidente vía API, sin depender de que el editor en el navegador sea perfecto. **Pendiente (Fase 2)**: el editor visual todavía no existe en producción — cuando exista, también debe impedir borrar un nodo de ese tipo en el canvas (mismo mecanismo ya validado en el spike de Fase 0, `.craft.custom.protected`), como segunda capa de defensa además de la validación server-side.

Con esto, "editable" significa layout/estilo/contenido alrededor de la lógica — nunca la lógica en sí. El resto de páginas (home, about, landings propias) no llevan `requires_nodes` y son completamente libres.

### Routing multi-página (consecuencia de "todas las páginas", a resolver en Fase 1)

Generalizar a `pages` con `slug` libre obliga a decidir cómo convive con las rutas fijas que ya existen en `web/app/[locale]/*` (`cataleg`, `disc/[id]`, `checkout`, `compte`, `blog`, `agenda`...):
- **Lista de slugs reservados** (los de arriba + cualquier ruta Core futura) que el admin no puede usar al crear una página — se valida server-side al crear/renombrar, mismo criterio que el vocabulario cerrado de `block_type`. Ya implementado (`RESERVED_PAGE_SLUGS`, `schemas/storefront.py`).
- El home sigue siendo un caso especial de `pages` (p. ej. `slug="home"` mapeado a `/`), no una tabla aparte.
- Una página de tenant que no colisiona con lo anterior necesita una ruta catch-all en `[locale]/[slug]/page.jsx` que resuelva contra `pages` por `tenant_id`+`slug`, 404 si no existe — a diseñar en Fase 1 junto con el modelo de árbol. **Esta misma ruta también resuelve `Pagina`** — ver §3e, no son dos catch-alls compitiendo.
- Gestión de navegación (qué páginas aparecen en el menú y en qué orden): pendiente de diseñar junto con la pantalla de admin, cuando `Page` tenga que asumir el rol de `Pagina.menu_visible`/`position` (§3e) — probablemente un campo equivalente en `pages`, no decidido todavía.

### e) `Page` sustituye a `Pagina` — no coexisten indefinidamente (decisión 2026-09-27)

Al construir el CRUD de `Page` se encontró que ya existe `Pagina` (`models/cms.py`): páginas con su propia ruta y presencia en el nav, con tres `type`: `estatica` (HTML libre), `llista-posts` (posts filtrados vía tabla `PostPagina`, con sidebar de archivo) y `agenda` (listado de eventos) — servidas hoy por el catch-all `web/app/[locale]/[pagina]/page.jsx`, el mismo espacio de URL que se diseñó para `Page`.

Mismo patrón que ya se aplica a `HomeBlock` (Fase 5: convive, se migra, se retira), extendido a `Pagina`:

- **`estatica` → `Page` es una mejora directa**: el HTML a pelo pasa a ser un árbol editable visualmente. Sustitución 1 a 1.
- **`llista-posts`/`agenda` → nodos "vivos" nuevos** (`blog_archive`, `agenda_list`), mismo patrón que `product_grid`/`carousel`: el nodo se posiciona/rodea de contenido libre en el árbol, pero su contenido (posts vía `PostPagina`, sidebar de archivo, paginación de eventos) lo sigue resolviendo el backend en cada request — no se convierte en algo editable a mano, ni se simplifica la lógica de `routers/blog.py` que ya existe.
- **Routing unificado**: el catch-all `[locale]/[slug]/page.jsx` de más arriba consulta `Page.published_tree` primero y cae a `Pagina` si no hay match — no dos catch-alls compitiendo por el mismo espacio de URL.
- **Retirada** (Fase 5, junto con `HomeBlock`): migrar cada `Pagina` existente a una `Page` equivalente (según su `type`, con las conversiones de arriba) y, con paridad alcanzada, retirar `Pagina`, `routers/blog.py`'s dependencia de ella, y la rama de fallback del catch-all.
- **Mientras tanto**: el guard de colisión de slug entre `Page`/`Pagina` (409, ya implementado en `routers/pages.py::_check_slug_available`) se mantiene sin cambios — es exactamente lo que hace falta durante la transición.

## 4. Pipeline de importación (server-side, nunca desde el navegador del tenant)

1. Tenant pulsa "Conectar Figma" → OAuth2 (app registrada en el developer portal de Figma) → callback guarda tokens vía `tenant_secrets.py`. **Construido, Fase 3.**
2. Tenant elige un frame de primer nivel de un fichero Figma → se encola un `FigmaImportJob` en Celery. **Construido, Fase 4** (`POST /admin/figma/import-jobs`).
3. El worker:
   - `GET /v1/files/:key` → recorre el árbol de nodos de Figma. **Construido.**
   - Frames con **auto-layout** → mapeo mecánico a `Stack` (el auto-layout de Figma está modelado sobre flexbox, mapeo razonablemente directo). **Decisión final, distinta de lo planteado aquí originalmente**: los frames sin auto-layout NO quedan como "mejor esfuerzo" — se omiten enteros con un aviso (ver §6, "no s'intenta resoldre amb heurístiques fràgils", y el checkpoint de Fase 4 en la bitácora). Vale la pena que el brief para cualquier UX/UI que se contrate pida auto-layout.
   - Estilos/variables de Figma (color, tipografía) → `ThemeTokens` del tenant. **Construido, Fase 3** (mapeo manual por el admin, nunca automático — ver `services/figma.py::get_file_design_styles`).
   - `GET /v1/images/:key` → exporta imágenes → sube al pipeline de assets ya existente (`/uploads/{uuid}.png`, mismo mecanismo que `logo_url`/`favicon_url`/`ReleaseImage`). **Construido, Fase 4** — siempre PNG, nunca SVG (ver saneamiento más abajo).
4. Resultado: borrador de `Page` + tokens actualizados. El tenant revisa en el editor y publica cuando quiera. **Construido**: `POST /admin/figma/import-jobs/{id}/apply` escribe en `draft_tree`, nunca en `published_tree`.
5. Mismo principio que Discogs (CLAUDE.md, punto 6): la API de Figma tiene rate limit — el cliente/navegador del tenant nunca la llama directamente, todo pasa por el worker. **Construido.**

Saneamiento: **decisión final, distinta de lo planteado aquí originalmente** — en vez de sanear SVG con el mismo mecanismo que `custom_css` (pensado para CSS, no para XML/SVG), las imágenes se exportan siempre como PNG. Un SVG puede llevar `<script>`/handlers (superficie XSS real) y construir un sanejador de SVG fiable es un problema propio, no una extensión trivial de `sanitize_custom_css` — se ha evitado el problema entero en vez de resolverlo a medias. Soporte de SVG queda pendiente de ese sanejador dedicado, si algún día hace falta.

### Bitácora detallada (histórico sesión a sesión — no hace falta leerlo para continuar, solo para entender el porqué de una decisión concreta)

#### Fase 0

**Checkpoint 2026-09-27 (primera sesión de spike, no las 1-2 semanas completas)**: PoC funcional en `web/app/admin/spike-editor-poc/` (ruta desechable, sin enlazar en ningún menú — **borrada el 2026-09-28** al confirmar que la Fase 1 real la supera), probado en vivo contra el stack de dev (`escaparate.localhost:8080`, `@craftjs/core` 0.2.12):

- **Confirmado**: Craft.js corre limpio sobre React 19 / Next 16.3 preview (declara el peer dependency, sin warnings en consola).
- **Confirmado**: el estado del editor (`query.serialize()`) se transforma sin pérdida al árbol `{id,type,props,style,children}` de §3, incluyendo props con el patrón locale `{ca,es,en}` — probado con drag&drop de un nodo nuevo desde la toolbox, no solo con el árbol inicial.
- **Confirmado**: un renderer separado (`TreeRenderer.jsx`, sin ningún `import` de `@craftjs/core`) renderiza ese árbol correctamente — la prueba concreta de que el runtime del editor no tiene que viajar al storefront público/SSR.
- **Gotcha real encontrado y corregido**: al serializar, `node.displayName` sale minificado en build de producción (`"tV"` en vez de `"Stack"`) porque ese campo cae al nombre de la función en runtime, que Next/Terser renombra. El campo correcto es `node.type.resolvedName` (la clave del objeto `resolver` pasado a `<Editor>`, que un minificador nunca toca porque es una clave de objeto, no un identificador). **Cualquier implementación futura de este transformador debe usar `resolvedName`, nunca `displayName`** — queda documentado aquí para no repetir el error en Fase 1.
- **Pendiente de esta primera sesión** (no descarta Craft.js, simplemente no se ha probado todavía): edición de breakpoints responsive, undo/redo, anidación profunda de canvases.

**Checkpoint 2026-09-27 (segunda sesión — panel de propiedades)**: añadido `related.settings` por tipo de nodo (patrón oficial de Craft.js) + `SettingsPanel.jsx` (`query.getEvent('selected').last()` + `node.related.settings`), probado en vivo:

- **Confirmado**: seleccionar un nodo distinto en el canvas cambia el panel de propiedades al `settings` correcto para ese tipo (probado Text → ProductGrid, cada uno con sus propios campos) — no hace falta un editor de props genérico, cada tipo de nodo aporta el suyo, mismo espíritu que un `PropsForm.jsx` por `block_type` hoy.
- **Confirmado end-to-end**: editar el campo "Text (es)" en el panel escribe vía `setProp` → se ve en `query.serialize()` → sobrevive la transformación `craftStateToTree` → aparece en `props.text.es` del árbol final. Round-trip completo de edición, no solo de lectura inicial.
- **Importante para §3d (nodos protegidos)**: Craft.js **no da "nodo no borrable por tipo" de fábrica**. Su `isDeletable()` solo protege nodos de nivel superior (`!isTopLevelNode()`) — cualquier otra protección (impedir borrar `checkout_form` en concreto) hay que construirla nosotros: interceptar el borrado según `node.data.custom` o similar, y ocultar/desactivar la acción de borrar en la UI para esos tipos. No es un bloqueo, pero confirma que ese punto de §3d/§6 es trabajo real de Fase 1, no algo que Craft.js resuelve solo.
- **Gotcha menor, no de arquitectura**: `node.data.displayName` (usado para mostrar el nombre del nodo seleccionado en el panel) sale igual de minificado que en el primer checkpoint ("tX", "tZ") — mismo motivo, mismo arreglo: para texto de cara al admin en el panel real habrá que usar una etiqueta propia por tipo (p. ej. un `label` en `.craft.custom`), no `displayName`, en ningún punto de la UI real.

**Checkpoint 2026-09-27 (tercera sesión — mecanismo de nodos protegidos, §3d)**: añadido `CheckoutFormPlaceholder` (representa `checkout_form`/`cart_summary`/`payment_widget`) con `.craft.custom = { protected: true }` y `rules.canDrag: () => false`, más un botón "Eliminar node" real en `SettingsPanel.jsx` (antes no existía ninguna forma de borrar nada en el PoC). Probado en vivo contra el stack de dev:

- **Confirmado**: `node.data.custom` sí lleva el `.craft.custom` estático del componente — `node.data.custom?.protected` se lee correctamente al seleccionar el nodo, sin necesidad de nada adicional.
- **Confirmado por comportamiento real, no solo por el flag deshabilitado en la UI**: intentar pulsar "Eliminar node" sobre `CheckoutFormPlaceholder` no lo borra (el botón `disabled` bloquea el `onClick`, se verificó clicando igualmente y comprobando que el nodo sigue en el árbol). El mismo botón sí borra un `TextNode` normal al primer clic — confirma que la protección es específica del tipo, no un bloqueo global accidental.
- **Reafirma el hallazgo del checkpoint anterior**: esto es enteramente lógica nuestra (`.craft.custom.protected` + comprobación en `SettingsPanel`) — Craft.js no ofrece "tipo no borrable" de fábrica, lo cual ya sabíamos, pero ahora está implementado y probado, no solo diagnosticado.
- **Pendiente, fuera de alcance de este checkpoint**: esto es SOLO la guarda del editor (cliente). La otra mitad de §3d — que `POST` a publicar una página rechace (422) si faltan los `requires_nodes` — no existe todavía porque no hay backend/modelo para esto (`pages`, `figma_import_jobs` siguen sin migrar). No dar por cerrado §3d hasta tener esa validación server-side también probada, no solo la de UI.

**Checkpoint 2026-09-27 (cuarta sesión — undo/redo y anidación de canvases)**: añadidos `HistoryBar` (`actions.history.undo/redo` + `query.history.canUndo/canRedo`, API oficial confirmada en los tipos de `@craftjs/utils`) y un botón "+ Secció" que crea un `<Element canvas is={Stack}>` desde la toolbox — el patrón oficial para contenedores anidables. Probado en vivo:

- **Confirmado — anidación real**: se creó una `Stack` dentro de la `Stack` raíz, y dentro de esa un `TextNode` — el árbol serializado muestra el segundo `Stack` con su propio `children` (no aplanado), y `TreeRenderer` lo renderiza anidado correctamente sin cambios (su recursión sobre `children` ya era genérica, no hizo falta tocarla).
- **Confirmado — undo/redo funciona sobre una secuencia compuesta**: "Desfer" ×2 deshizo, en orden, la creación del `TextNode` anidado y luego la creación de la `Stack` contenedora, devolviendo el árbol a su estado original de 3 nodos. "Refer" ×2 recuperó ambos pasos exactamente. Sin errores de consola en toda la secuencia.
- **Sin sorpresas**: a diferencia de los checkpoints anteriores, aquí no hubo ningún gotcha — undo/redo y anidación funcionan tal como los documenta Craft.js, sin necesidad de trabajo extra nuestro (a diferencia de los nodos protegidos, que sí lo requirieron).

**Checkpoint 2026-09-27 (quinta sesión — breakpoints responsive)**: añadido `breakpoints.js` (cascada `base → tablet → mobile`, fallback hacia arriba si falta un nivel — mismo espíritu que el fallback a `ca` del patrón de idiomas) y `BreakpointContext.jsx` (estado compartido de qué breakpoint se edita/previsualiza). `Stack.direction`/`Stack.gap` pasan de valor plano a objeto `{base, tablet?, mobile?}`; `StackSettings` gana un selector Desktop/Tablet/Mòbil que edita el nivel activo y un botón "Treure override" por nivel.
